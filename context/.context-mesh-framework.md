# Context Mesh Framework

## Overview

Context Mesh keeps the durable context of a project close to its code. Its loop is **Intent → Build → Learn**:

1. **Intent** records the problem, value, and intended behaviour before implementation.
2. **Build** implements approved intent while following recorded decisions and patterns.
3. **Learn** records outcomes, changes, and significant lessons after implementation.

## File Type Separation

- `intent/project-intent.md` and `intent/feature-*.md` describe **what** exists or is wanted and **why** it matters. Feature files may include functional acceptance criteria, but never implementation details, library names, source paths, or code examples.
- `decisions/*.md` are ADR-style records of **technical choices**: architecture, libraries, integration approaches, rationale, and alternatives.
- `knowledge/patterns/*.md` document **how to implement** recurring code structures. They contain concrete examples and point to files using them.
- `knowledge/anti-patterns/*.md` documents approaches that should be avoided and their safer replacement.
- `agents/` is reserved for scoped agent instructions when required.
- `evolution/changelog.md` records contextual changes and learning over time.

## Plan, Approve, Execute (Mandatory)

For changes beyond a small, already-approved correction:

1. Plan the feature intent and any technical decision.
2. Obtain approval for the proposed scope and decisions.
3. Execute the implementation using documented patterns.

Do not silently turn a feature file into an implementation plan. Document an ADR before implementing a material new technical approach.

## When to Create Files

Create a feature file for a distinct user-facing capability or material change in behaviour. Create a decision file when a technical choice is consequential, reusable, or has alternatives worth preserving. Create a pattern file when code structure is repeated or should be deliberately reused. Do not create files for trivial refactors, obvious language syntax, or one-off implementation details.

## Context Structure

```text
context/
├── .context-mesh-framework.md
├── intent/
├── decisions/
├── knowledge/
│   ├── patterns/
│   └── anti-patterns/
├── agents/
└── evolution/
```

## Bidirectional Links

Use relative Markdown links. Features link to applicable decisions and patterns; decisions link back to affected features; patterns link to their supporting decisions and features. Keep links bidirectional whenever the relationship is material. A feature may reference a pattern, but must not copy its implementation content.

## Status Requirements

Every feature and decision includes a `Status` section with creation date, phase, and current state. Patterns include creation date and state. Existing-code documentation must say when its rationale or alternatives are inferred rather than explicitly recorded.

## Definition of Done

A completed implementation has an approved intent (and ADR where required), follows relevant decisions and patterns, has proportionate verification, updates affected Context Mesh files, and adds an evolution entry. Documentation of existing code instead records the current state faithfully without inventing unimplemented work.
